# Insurance Claim Cycle-Time & Documentation Monitor

A workflow-analytics tool that rebuilds each insurance claim's case history from messy source extracts,
measures how long every stage takes, finds incomplete cases and bottleneck stages, and produces a traceable
backlog report. It measures **time and completeness only** - it never decides whether a claim is eligible or payable.

All data is synthetic (generated by `generate_data.py`), so there is nothing confidential in this project.

---

## Quick start (step by step)

Requires Python 3.10 or newer.

**1. Open a terminal in this folder** (the one containing `app.py`).

**2. Create and activate a virtual environment**

macOS / Linux:
```bash
python3 -m venv .venv
source .venv/bin/activate
```
Windows (PowerShell):
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

**3. Install the packages**
```bash
pip install -r requirements.txt
```

**4. Start the dashboard** (the zip already contains the generated data and `claims.db`)
```bash
streamlit run app.py
```
It opens at http://localhost:8501.

**Rebuild everything from scratch (optional)**
```bash
python generate_data.py      # writes data/raw/*.csv  (600 messy claims, seed 42)
python pipeline.py           # cleans, reconstructs histories, writes claims.db, prints the data-quality log
python export_report.py      # writes report.html and findings.md
streamlit run app.py
```
`python generate_data.py --n 1000 --seed 7` creates a different dataset. `python pipeline.py --as-of 2026-12-01`
re-ages open claims to another snapshot date.

## What is in the folder

| File | Purpose |
|---|---|
| `generate_data.py` | Builds five messy source extracts plus a hidden ground-truth file used only for self-testing |
| `pipeline.py` | Cleaning, case-history reconstruction, measures, SQLite storage, self-test |
| `analytics.py` | Summary measures and the plain-language findings |
| `charts.py` | Plotly charts (validated colour palette, one fixed colour per stage) |
| `app.py` | Streamlit dashboard |
| `export_report.py` | Self-contained `report.html` and `findings.md` (no Streamlit needed) |
| `claims.db` | SQLite database: raw copies, cleaned tables, timeline, durations, summary, backlog, data-quality log |
| `data/raw/` | The five source CSV extracts |
| `findings.md` / `report.html` | Short interpretation and a browsable report |

## Source data (`data/raw/`)

| File | Content | Problems deliberately included |
|---|---|---|
| `claims.csv` | one row per claim, **status field overwritten** with only the latest value | spelling variants, "Rs. 1,25,000" amounts, mixed date formats, missing region/amount, stale duplicate rows, stale status |
| `status_history.csv` | status change events | about 10% of events never logged, duplicates and near-duplicates, orphan claim ids, future-dated typos, unknown labels, out-of-order timestamps |
| `documents.csv` | required-document checklist | name variants, received before requested, status contradicting dates, dates lost, duplicates |
| `adjusters.csv` | adjuster assignments | id formats (`adj07`, `ADJ 07`), duplicates, claims with no assignment |
| `payments.csv` | payment events | type/status variants, failed attempts, duplicates, some final payments missing |

## How the case history is rebuilt

Stages: Reported -> Registered -> Document Collection -> Assessment -> Settlement Processing -> Payment Issued -> Closed.

For each stage the entry time is taken from the best available evidence, in this order:
1. the status-history event;
2. the claim's current status + last-updated time (when that status is this stage);
3. domain evidence: first adjuster assignment (Registered), first document request (Document Collection),
   last required document received (Assessment), first successful final payment (Payment Issued).

Each entry stores its **source, source record id and confidence**. If the best evidence contradicts the stage order
it is set aside and the next-best is used. The pipeline checks itself against the generator's ground truth:
about 99% of rebuilt stage entries land within one day of the truth.

## Measures

| Measure | Definition |
|---|---|
| Stage duration | entry of a stage to entry of the next evidenced stage (open stages run to the snapshot date) |
| Total turnaround | report to closure, closed claims only (median, mean, P90) |
| Bottleneck score | a stage's share of all elapsed claim-days, completed plus still-open |
| Incomplete case | missing required document, history gap, status field disagreeing with history, no adjuster record, or no final payment record |
| Backlog | claims not closed in the rebuilt history; days in stage, days over target, what each is waiting on, and the record behind the stage entry |

## Dashboard tabs

Overview (KPIs, interpretation, charts) - Stages & bottlenecks - Incomplete cases - Backlog report (filter, CSV download) -
Case inspector (rebuilt timeline, evidence per stage, original raw rows) - Data quality - SQL console (read-only) - Method.
Sidebar filters: claim type, region, reported date, editable stage targets.

## Limitations

- A closed claim can look open if its closure event is missing **and** its status field is stale.
- Stages with no evidence at all cannot be timed; their time is left out of per-stage statistics by default
  (switch in the sidebar).
- Adjuster comparisons use each claim's latest adjuster and ignore claim mix.
- Findings are observational associations, not causal claims.

## Using real data

Keep the same five files and column names (or edit the mapping dictionaries at the top of `pipeline.py`), put them in
`data/raw/`, and run `python pipeline.py`. The ground-truth self-test is skipped automatically when no truth file exists.
